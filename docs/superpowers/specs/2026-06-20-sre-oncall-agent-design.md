# SRE 值班答疑 Agent 设计

## 背景

需要做一个面向工程/SRE 值班场景的答疑 Agent。第一版聚焦 API 服务 5xx 升高和延迟升高问题，帮助值班同学快速理解告警、查找 SOP、收集只读证据，并给出下一步排查建议。

当前不追求自动修复线上故障，而是先做一个可靠、可解释、可替换数据源的 Web demo，为后续接入真实监控、日志和告警系统打基础。

## 目标

- 提供 Web 聊天入口，支持值班同学用自然语言提问。
- 支持 API 服务 5xx / 延迟升高场景的排查问答。
- 检索 SOP、Runbook、FAQ 和服务说明，并在回答中引用证据。
- 通过只读工具查询告警、指标、日志和服务目录。
- 底层先用 mock adapter，后续可替换为 Prometheus、Alertmanager、Grafana、Loki、ELK 或云监控。
- 输出结构化诊断卡，包含初步判断、证据、下一步排查、升级建议和边界说明。
- 在信息缺失、工具失败、证据冲突或低置信度时保持诚实降级。

## 非目标

- 第一版不执行任何线上修复动作。
- 第一版不做回滚、重启、扩容等写操作。
- 第一版不做完整事件工作台、工单流转或多租户权限后台。
- 第一版不接真实生产系统；真实系统通过后续 adapter 替换接入。

## 用户场景

典型问题：

```text
checkout-api 5xx 升高怎么办？
```

系统应该能够识别服务名、症状和默认时间窗口，查询 mock 告警、指标、日志和 SOP，然后给出带证据的排查建议。如果问题缺少服务名或时间窗口，系统应该先追问。

## 架构

```text
Web Chat UI
    |
    v
SRE Agent Orchestrator
    |
    +-- Knowledge Base
    |     +-- SOP
    |     +-- Runbook
    |     +-- FAQ
    |     +-- 服务说明
    |
    +-- Alert Tool
    +-- Metric Tool
    +-- Log Tool
    +-- Service Catalog Tool
```

### Web Chat UI

负责展示聊天输入、回答结果和诊断卡。第一版只需要支持一个主聊天页面，重点展示：

- 用户问题。
- Agent 的结构化回答。
- 证据列表。
- 工具失败或降级说明。
- 数据时间戳和边界说明。

### SRE Agent Orchestrator

负责对话编排和工具调用决策：

- 解析用户问题中的服务名、症状和时间窗口。
- 判断是否需要追问缺失信息。
- 调用知识库检索 SOP。
- 并行或串行调用只读工具查询告警、指标、日志和服务目录。
- 汇总证据，生成结构化诊断卡。
- 在低置信度或证据不足时给出下一步取证建议，而不是强行判断根因。

### Knowledge Base

第一版可以使用本地 Markdown 或 JSON 样例文档，内容包括：

- `checkout-api` 5xx 排查 SOP。
- API 延迟升高排查 SOP。
- 下游依赖超时处理说明。
- 服务 owner 和升级路径说明。

后续可以替换为向量检索、OpenAI File Search 或企业内部知识库。

### 只读工具接口

所有工具都以稳定接口暴露，第一版用 mock 数据实现。

- `AlertTool`：查询当前 firing 告警、告警等级、开始时间和影响服务。
- `MetricTool`：查询 5xx rate、P95/P99 latency、QPS、CPU、内存等时间序列摘要。
- `LogTool`：查询错误日志摘要、Top exception、示例 trace 或 request id。
- `ServiceCatalogTool`：查询服务 owner、依赖关系、升级联系人和相关 runbook。

工具接口必须返回数据时间戳，方便回答中说明证据时效。

## 数据流

1. 用户在 Web Chat UI 输入问题。
2. Orchestrator 解析服务名、症状和时间窗口。
3. 如果关键信息缺失，返回追问。
4. 如果信息足够，检索 SOP 和服务说明。
5. 调用 Alert Tool 查询当前告警。
6. 调用 Metric Tool 查询 5xx、延迟和流量趋势。
7. 调用 Log Tool 查询错误日志摘要。
8. 调用 Service Catalog Tool 查询 owner、依赖和升级路径。
9. Orchestrator 汇总证据，识别可能原因、置信度和缺失信息。
10. Web Chat UI 展示结构化诊断卡。

## 回答结构

每次完整回答应该包含：

- **初步判断**：当前最可能的问题方向，必须避免把相关性说成确定因果。
- **证据**：列出来自告警、指标、日志和 SOP 的关键证据。
- **下一步排查**：给值班同学可以执行的只读检查步骤。
- **升级建议**：说明什么时候需要升级给服务 owner 或值班负责人。
- **边界说明**：说明没有执行修复动作，并标注工具失败、数据过期或证据不足等情况。

示例：

```text
初步判断：checkout-api 的 5xx 升高更像是下游 payment-gateway 超时引发。

证据：
- 14:05 后 P95 延迟从 180ms 升到 2.4s。
- 错误日志 Top exception 为 UpstreamTimeoutError。
- 当前 Alert: checkout-api-high-5xx firing。

建议：
1. 先确认 payment-gateway 当前错误率和延迟。
2. 检查最近 30 分钟 checkout-api 是否有发布。
3. 若 10 分钟内未恢复，按 SOP 升级 payment owner。

边界：我没有执行任何修复动作；当前结论基于 mock 监控和日志证据。
```

## 错误处理

- **信息缺失**：缺服务名、症状或时间窗口时先追问。
- **工具失败**：明确显示失败，并降级为 SOP 答疑或部分证据分析。
- **证据冲突**：列出冲突点，不强行给确定根因。
- **低置信度**：给下一步取证路径，不装作已经定位问题。
- **高风险建议**：可以建议检查回滚、扩容或降级方案，但不能自动执行。
- **数据过期**：回答中展示数据时间戳，过期时提醒重新查询。

## 测试策略

### Adapter 单元测试

覆盖 mock 工具的正常返回、空结果、异常和数据过期场景。重点保证工具输出结构稳定，错误可被 Orchestrator 识别。

### Agent 场景测试

覆盖以下核心用例：

- `checkout-api 5xx 升高怎么办？` 能输出带证据诊断卡。
- 缺少服务名时先追问。
- 日志工具失败时明确降级，不编造日志数据。
- 指标和日志证据冲突时列出冲突，不强行定位根因。
- 低置信度时输出下一步取证建议。

### Web 集成测试

验证聊天 UI 能提交问题并展示：

- 诊断摘要。
- 证据列表。
- 下一步排查建议。
- 工具失败提示。
- 边界说明。

## 验收标准

- 给定 mock 告警 `checkout-api 5xx 升高`，系统能在 Web 页面输出结构化诊断卡。
- 回答至少包含一条告警证据、一条指标证据、一条日志证据和一条 SOP 引用。
- 日志工具失败时，系统明确显示降级说明，并继续基于剩余证据回答。
- 系统不会声称执行了修复动作。
- mock adapter 可以通过统一接口替换为真实监控、告警或日志系统。

## 后续扩展

- 接入真实 Prometheus / Alertmanager / Grafana / Loki / ELK。
- 增加事件时间线和证据面板，演进为完整事件工作台。
- 接入工单系统或群通知，但写操作必须经过人工确认。
- 增加权限和审计，限制不同用户可查询的服务范围。
- 引入离线评测集，持续评估回答是否有证据、是否过度断言、是否正确降级。
