# 上下文工程：人与 AI 协作的需求完成模型

> **一句话本质**：上下文工程是让 AI 从"每次对话都是第一次见面"变成"这个项目的长期协作者"的系统性方法。它解决的不是 AI"会不会写代码"，而是"知不知道自己在写什么项目、之前达成了什么共识"。

---

## 一、核心问题：AI 的三重失忆

传统 AI 编程助手有一个根本缺陷：**它没有持久状态**。每次启动都是全新进程，之前的一切对它来说都不存在。

这导致三个具体问题：

### 问题一：跨会话失忆

**场景**：周一你和 Claude 花了 2 小时讨论认证方案，决定用 JWT + Redis 黑名单。周三你打开新会话，说"继续把认证做完"。

```
用户：继续把认证模块做完
Claude：好的！请问你想用什么认证方案？JWT？Session？OAuth？
用户：？？？周一不是定了吗
Claude：（完全不知道你在说什么）
```

**本质**：AI 的"记忆"只存在于当前会话的上下文窗口。新会话 = 全新的大脑。

### 问题二：项目知识缺失

**场景**：你的项目约定所有 API 错误必须抛异常，由全局中间件处理。禁止在 Controller 里返回 `{ error: "xxx" }`。

```
用户：帮我写个登录接口
Claude：（基于通用知识生成）
if (!user) {
  return res.status(400).json({ error: 'Invalid credentials' });
}
```

**用户**：不对，我们项目不这么写。然后花 3 轮对话解释规范。

**本质**：AI 有全世界的通用知识，但**没有你的项目的特定知识**。

### 问题三：长会话注意力稀释

**场景**：长会话里，第 3 轮明确说了"所有新接口必须加管理员权限校验"。编码到第 20 轮时你问"这个接口的权限校验做了吗？"

```
Claude：接口里我没有看到权限校验，需要我加上吗？
用户：？？？第 3 轮不是明确说了吗
Claude：（早期内容已被挤出上下文窗口）
```

**本质**：上下文窗口有限，早期的重要决策会被压缩、摘要甚至丢失。AI 不是"忘了"，而是"根本没看到"。

---

## 二、三层上下文架构

三层上下文不是平行的，而是**逐层收敛**：

```
项目级（基座）        → "在这个项目里，我们怎么做事"
    ↓
迭代级（精确指令）    → "本次迭代要做什么、不做什么"
    ↓
实时级（现场数据）    → "此时此刻，具体文件长什么样"
    ↓
              代码产出 + 决策回流
```

**贯穿案例**：为电商订单系统增加"优惠券"功能。

---

### 第一层：项目级上下文（寿命：永久）

**作用**：定义项目的行为基线。AI 每次启动自动读取。

**载体**：`CLAUDE.md` + `.claude/rules/*.md`

**内容**：技术栈、架构约束、编码风格、通用模式

**示例**：

```markdown
# CLAUDE.md

## 技术栈
- Runtime: Node.js 20 LTS
- ORM: Prisma 5.10
- Cache: Redis 7

## 架构约束
- 严格三层：Controller → Service → Repository
- Controller 只做参数校验、调用 Service、返回响应
- Service 做业务规则、事务控制
- Repository 做纯数据库操作

## 通用规则
- 所有 API 错误必须抛出继承自 AppError 的异常
- 数据库操作必须在 Service 层用 prisma.$transaction() 包裹
- Redis key 统一格式：`{service}:{entity}:{id}`
```

```markdown
# .claude/rules/api-design.md

- RESTful，资源名词复数
- 分页统一用 cursor-based，禁止 offset
- 响应体统一包装：{ data, meta?, error? }

- 400: 参数校验失败
- 409: 业务冲突
- 422: 业务规则不满足
```

```markdown
# .claude/rules/state-management.md

- 敏感操作必须用数据库事务
- 事务内禁止调用外部 HTTP 接口
- 库存类表必须带 version 字段（乐观锁）
- 读多写少数据可缓存，TTL 5 分钟
- 写操作后立即删除缓存
```

**效果**：团队新成员启动 Claude 时，AI 自动知道"我们用 Prisma""错误要抛异常""Redis key 怎么命名"。

### 第二层：迭代级上下文（寿命：1-2 周）

**作用**：定义本次迭代的精确边界和决策。通过 `--context` 注入。

**载体**：`.claude/iterations/YYYY-MM-DD-feature-name.md`

**内容**：需求范围、业务规则、技术决策、接口契约、改动影响面、显式边界

**示例**：

```markdown
---
id: EC-2026-0419
type: feature
affected:
  - src/services/order.ts
  - src/services/coupon.ts（新增）
  - src/controllers/coupon.controller.ts（新增）
  - src/repositories/coupon.repository.ts（新增）
  - prisma/migrations/20260419_add_coupon_tables.sql
---

## 需求背景
用户在下单时可选择一张优惠券，系统实时计算优惠后金额。
本次迭代仅支持"满减券"（如满 100 减 20），不支持折扣券和叠加使用。

## 业务规则
1. 一张订单最多使用 1 张优惠券
2. 优惠券使用门槛按"优惠前订单金额"计算
3. 优惠券必须在有效期内（精确到秒）
4. 用户已领取的优惠券每人限用 1 次
5. 以下情况不可用：金额未达门槛、已过期、已被使用、商品在排除类目
6. 优惠金额不能超过订单优惠前金额的 50%（风控规则）

## 技术决策记录
1. **优惠券计算放在订单 Service，不独立服务**
   - 理由：避免分布式事务，当前订单量单机事务足够
2. **优惠券领取与使用分开建表**
   - coupon_template（模板）：创建时写入，基本不变
   - user_coupon（用户领取记录）：领券时写入，状态机驱动
3. **优惠金额计算时机**：订单创建时计算并写入，不实时重算
   - 理由：防止支付前修改购物车导致优惠变动

## 接口契约

### POST /api/v1/coupons/{id}/claim
- 幂等：同一用户重复领取返回 409 CONFLICT

### GET /api/v1/coupons/available
- Query: orderAmount, categoryIds
- 返回按优惠力度降序排列

### POST /api/v1/orders（修改现有接口）
```json
{
  "items": [...],
  "couponId": "string?"
}
```
- 若 couponId 不可用，返回 422 COUPON_NOT_APPLICABLE
- 响应增加 discountAmount, finalAmount

## 改动影响面
- 订单创建流程：增加优惠券校验和金额计算
- 订单详情查询：增加优惠金额展示
- 数据库：新增 coupon_template, user_coupon 表
- **不改动**：支付回调、库存扣减、前端代码

## 待验证假设
- [ ] 优惠券查询是否需要分页？
- [ ] 高并发领券，乐观锁重试策略是否足够？
```

**注入**：
```bash
claude --context .claude/iterations/2026-04-19-coupon-system.md
```

**关键**：必须显式声明**边界**（不改什么），防止 AI "顺手"改无关模块。

### 第三层：实时级上下文（寿命：单次会话）

**作用**：在注意力稀释前，锚定"此时此刻"的关键信息。

**核心洞察**：实时级上下文管理的本质不是"给 AI 更多信息"，而是"在注意力窗口坍塌前，用策展人的方式确保关键信息被锚定"。

#### 注意力不是无限的：200K token ≠ 200K 有效注意力

Claude Code 的上下文窗口是 200K，但模型对上下文的**有效注意力**远小于这个数字。超过阈值后，模型对开头和中间信息的"分辨率"急剧下降。

| 指标 | 阈值 | 含义 |
|------|------|------|
| 有效上下文上限 | ~256K | 超过后模型质量可测量下降 |
| 建议利用率 | 75% | 90%+ 时产出更多但质量更低 |
| 自动压缩触发 | ~167K (83%) | 系统开始 summary 替换历史 |

#### Claude Code 的压缩机制

当会话接近上限时，触发 **compaction**：

1. **触发**：默认 83% 容量时自动触发（200K ≈ 167K tokens）
2. **方式**：独立模型调用把历史对话压缩成结构化摘要
3. **压缩后保留**：
   - **9 个 section**：用户意图、技术栈、改动文件、遇到的错误、尝试的方案、用户原话、待办工作、项目状态、下一步行动
   - 最近访问的最多 5 个文件（每个 5K tokens）
   - 后台任务状态

**压缩是 lossy 的**：

| 通常保留 | 通常丢失 |
|---------|---------|
| 当前任务和即时上下文 | 早期会话的指令（如"不要碰这个文件"） |
| 最近修改的文件名 | 50+ 条消息前的具体代码片段 |
| 最近的错误和解决方案 | 选择方案 A 而非 B 的推理过程 |
| 用户原话 | 微妙风格规则 |

#### 深度案例：一个长会话中的注意力坍塌

**背景**：实现优惠券系统，已进行 30 轮讨论。

**第 5 轮**（注意力充足）：
```
用户：优惠券计算放在订单 Service 里，不要独立服务
Claude：明白，我会在 OrderService 里增加 applyCoupon 方法
```

**第 25 轮**（接近 token 上限，早期上下文被压缩）：
```
用户：帮我写一下优惠券查询的 Repository
Claude：（把查询逻辑拆到独立的 CouponRepository）
用户：等等，不是说了计算逻辑放 OrderService 吗？
Claude：抱歉，我可能遗漏了之前的讨论...
```

**诊断**：压缩丢失了"决策理由"，只保留了"做了什么"的摘要。AI 看到"写了 CouponRepository"，但不知道为什么这和"不拆服务"矛盾。

#### 人的主动管理策略

面对注意力稀释，人需要扮演**上下文策展人**。

**策略 1：显式锚定关键决策**
不要假设 AI 会记住。关键决策用不可压缩的方式锚定——写入迭代卡片或 CLAUDE.md，而非仅在对话中声明。

**策略 2：分阶段会话**
```
会话 A：讨论方案、确定决策、生成迭代卡片（Clarify + Contextualize）
会话 B：基于卡片编码（Explore）
会话 C：代码 review、测试、收尾（Converge）
```
每个会话控制在 15-20 轮内，避免触及压缩阈值。

**策略 3：主动压缩**
```
/compact focus on the coupon calculation logic and the decision
to keep it in OrderService. Drop the test debugging details.
```
在 80% 之前主动压缩，此时模型"分辨率"还足够高，摘要质量更好。

**策略 4：Subagent 隔离脏工作**
```
用户：帮我找一下整个项目里所有用到旧版认证逻辑的地方，
      用子代理做这件事，只把结论带回来
```
搜索、探索性重构等产生大量中间结果的工作交给 Subagent，主会话只接收结论。

#### 实时注入示例

**人主动注入**：
```
先看一下现有订单流程 @src/services/order.ts，
我需要在 calculateTotal 之后加入优惠券计算。

数据库 schema 在这里 @prisma/schema.prisma，
看看 order 表现有字段，我需要加 discountAmount。
```

**运行时反馈**：
```
我按你的写法跑了测试，报错了：

Error: P2025: record_not_found, coupon_template

测试数据明明插入了，帮我看看
@src/repositories/coupon.repository.ts 的查询逻辑。
```

**AI 修正**：发现 repository 用 `findUnique({ where: { code } })` 查询，但测试数据用 `id` 插入。修正为 `findUnique({ where: { id: couponId } })`。

### 三层协作效果

| AI 读取 | 获得的信息 | 产生的代码特征 |
|---------|-----------|--------------|
| 项目级 | "错误必须抛异常" | 自动 `throw new AppError(...)` |
| 迭代级 | "优惠金额不能超过 50%" | 在 Service 层加入校验逻辑 |
| 实时级 | `calculateTotal` 返回 `Decimal` | 自动用 Decimal 运算，不用 Number |

**缺少任何一层的后果**：

| 缺少层级 | 后果 |
|---------|------|
| 无项目级 | 用错 ORM、错误处理风格不统一、架构分层混乱 |
| 无迭代级 | "顺手"改无关模块、遗漏业务规则、推翻已有决策 |
| 无实时级 | 基于假设写代码，运行时出错 |

## 三、PAC 协作模型：人机权力的动态博弈

PAC 不是"三步走"的线性流程，而是**人-AI 之间持续进行的权力边界谈判**——谁拥有架构决策权、谁拥有业务规则定义权、谁拥有实现细节权。

```
Phase 1: Clarify（意图澄清）
    │ 人提出粗糙意图 → AI 反问暴露假设 → 人修正补充
    │ 产出：《意图共识》
    ▼
Phase 2: Contextualize（上下文构建）
    │ 边界精确 + 实现留白
    │ 产出：《迭代上下文卡片》
    ▼
Phase 3: Explore & Converge（探索与收敛）
    │ AI 提案 → 人判断价值 → 人决策 → AI 根据决策模式调整
    │ 反馈环周期：秒/分钟
    │ 产出：代码 + 更新决策记录（回流）
```

### Phase 1 Clarify：不是问答，是假设暴露

Clarify 的核心不是"AI 问、人答"，而是**暴露双方隐含的假设**。

**失败的 Clarify**：
```
用户：帮我做个优惠券系统
Claude：您想要什么类型的优惠券？满减券、折扣券、还是随机立减？
用户：满减券就行
...（20 轮后进入编码）

两周后 PM：优惠券不能和会员折扣叠加，你们怎么没做互斥规则？
```

AI 的追问停留在技术参数，没有触及业务边界。**Clarify 的深度标准**：

| 浅层 Clarify | 深层 Clarify |
|-------------|-------------|
| 问技术参数（字段类型、有效期精度） | 问业务规则边界（和谁互斥、什么场景不可用） |
| 问"怎么做" | 问"为什么做"（解决什么痛点、成功衡量标准） |
| 假设用户知道所有需求 | 主动暴露隐式假设（"我假设这是给 C 端用户的，对吗？"） |
| 一轮问答结束 | 多轮追问直到"没有新的信息出现" |

**人的责任**：不能只给技术指令，要主动暴露业务上下文。AI 问不到的地方，人要主动补充。

### Phase 2 Contextualize：边界精确，实现留白

Contextualize 的关键张力：**卡片越精确，AI 发挥空间越小；卡片越模糊，AI 越容易偏离。**

| 过度精确 | 过度模糊 |
|---------|---------|
| 规定每行代码怎么写 | 只说"做个优惠券系统" |
| AI 变成代码抄写员 | AI 自由发挥，偏离业务目标 |
| 适用于安全关键代码 | 适用于探索性原型 |

**正确的做法**：

```markdown
## 业务规则（精确、不可协商）
- 一张订单最多 1 张优惠券
- 优惠金额不超过订单金额的 50%

## 技术约束（精确、不可协商）
- 不改支付回调逻辑
- 优惠券计算在 OrderService 中

## 实现细节（留白、AI 自由发挥）
- 具体的数据库索引策略
- 缓存的粒度
- 单元测试的覆盖率目标
```

### Phase 3 Explore & Converge：权力的流动

不是"AI 写、人看、人说不行、AI 改"的循环。而是：

> **AI 提出方案 → 人判断价值 → 人决定修正/否决/接受 → AI 根据人的决策模式调整后续提案。**

**深度案例**：

```
Claude：我写了优惠券计算的初步实现，放在 OrderService 里。
       为了处理并发，我使用了数据库行锁（SELECT FOR UPDATE）。

用户：等等，行锁会不会导致性能问题？活动期间可能有大量并发领券。

Claude：您说得对。替代方案：
       A. 乐观锁（version 字段），冲突时重试
       B. 预扣库存 + 异步确认
       C. 保持行锁，但加 Redis 分布式锁做第一层过滤
       考虑到您之前提到的"当前订单量单机事务足够"，我倾向 A。

用户：选 A。但重试不要超过 3 次，第 3 次失败直接抛
       TooManyRequests 错误。

Claude：明白。我更新实现。
       同时我注意到，这个重试逻辑可能也适用于库存扣减。
       需要我把这个模式提取成可复用的装饰器吗？

用户：暂时不要。本次只改优惠券，库存是另一个迭代。
       但这个建议很好，记到迭代卡片的"待验证假设"里。
```

**这个对话中的权力分配**：

| 步骤 | 谁主导 | 权力类型 |
|------|--------|---------|
| AI 提出初始方案 | AI | 技术实现权 |
| 人挑战技术假设 | 人 | 业务场景判断权 |
| AI 提供选项分析 | AI | 技术方案枚举权 |
| 人做选择并附加约束 | 人 | 业务规则定义权 |
| AI 执行并识别模式复用 | AI | 模式识别权 |
| 人否决范围蔓延 | 人 | 范围控制权 |

**如果人在最后说"好，顺手把库存也改了吧"**——这就是范围蔓延，是 PAC 中最常见的失败模式。

### 权力分配的一般原则

| 决策类型 | 谁主导 | 为什么 |
|---------|--------|--------|
| 架构选择（单体 vs 微服务） | 人 | 影响团队长期维护和部署成本 |
| 算法选择 | AI | 纯技术问题，AI 知识更全面 |
| 命名规范 | 项目级规则 | 已预先确定 |
| 错误消息文案 | 人 | 面向用户，需要产品和语言判断 |
| 性能优化取舍 | 人 | 价值判断，取决于业务场景 |

### PAC 的失败模式与回退策略

| 失败模式 | 症状 | 回退策略 |
|---------|------|---------|
| **Clarify 停滞** | AI 反复问同样的问题 | 人主动总结："我理解你的问题是 X、Y、Z，对吗？" |
| **Contextualize 过度** | 卡片 300 行，AI 不知从何下手 | 删除实现细节，只保留边界和决策 |
| **Explore 发散** | AI 每轮都提出新方向，从不收敛 | 人明确说："基于当前方案，只做这三处修改，其他不动" |
| **Converge 妥协** | 人累了，对明显有问题的代码说"先这样吧" | **立即暂停**，/compact 后新开会话，或让同事 review |
| **上下文坍塌** | 长会话中早期决策丢失，AI 开始重复错误 | 主动 /compact 锚定关键决策，或分阶段重启会话 |
| **范围蔓延** | 人同意 AI 的"顺手"建议，迭代失控 | 回到迭代卡片，核对"不改动"列表 |

### 与传统流程的核心差异

| 维度 | 传统流程 | PAC 模型 |
|------|---------|---------|
| 优化目标 | 人-人信息传递效率 | 人-AI 认知对齐效率 |
| 验证时机 | 阶段结束时（事后） | 实时进行（事中） |
| 文档角色 | 传递信息的媒介 | 可执行的上下文 |
| 返工成本 | 高（发现时已做完） | 低（分钟级纠偏） |
| 人的角色 | 执行者 + 检查者 | 决策者 + 验证者 + 策展者 |
| 核心机制 | 串行阶段 | 人机权力动态博弈 |

## 四、规范驱动编程：从传统 SDD 到 AI 工具谱系

### 同构与异构

两者都是"对齐上下文"的机制，结构相似（需求、约束、决策、接口契约）。但消费它们的主体不同——**人脑 vs 语言模型**——这导致了根本性的差异。

### AI 时代的 SDD 工具谱系

当前主流的 AI 编程辅助工具在"规范驱动"这个方向上形成了三个有代表性的流派，它们的差异本质上是**对"约定应锚定在哪里"的不同理解**。

| 维度 | **OpenSpec** | **SpecKit** | **Superpowers** |
|------|-------------|-------------|-----------------|
| **本质** | 意图的版本控制系统 | 瀑布式规格工作流 | 可复用的行为纪律 |
| **核心产出** | `specs/` + `changes/`（带 ADDED/MODIFIED/REMOVED 标记的活文档） | `.specify/` 下的多层 markdown 套件（constitution + spec + plan + tasks） | `SKILL.md` 行为约束文件 |
| **与代码的关系** | 规格与代码**解耦**，规格先行、代码后补 | 规格与代码**伴生**，一一映射 | 规格与代码**融合**，纪律渗透执行过程 |
| **设计哲学** | 轻量、显式 diff、可追溯 | 完整、严谨、可追溯 | 自动、约束、可组合 |
| **适用场景** | 在成熟系统上变更（1→n） | 从零构建复杂系统（0→1） | 已有规格但执行走样 |

**OpenSpec** 的核心创新是 **Delta 契约**——用显式标记（ADDED/MODIFIED/REMOVED）描述"相对于当前系统状态，需要做什么改变"。这使它天然适合 Brownfield（现有系统演进），现有规格就是基线，变更天然有上下文。但它意图层薄弱，规格本身不含"为什么"。

**SpecKit** 的核心价值是 **六阶段 slash 命令工作流**（constitution → specify → clarify → plan → tasks → analyze → implement）。其中 `/speckit.clarify` 最有价值——在编码前强制暴露并消解歧义。但它的规格是静态的，写完后不会随实现自动演化，容易产生 spec drift；且 800+ 行 markdown 对 token 和注意力都是负担。

**Superpowers** 的核心是 **行为纪律**——它不规定"写什么规格"，而规定"怎么思考"。AI 自动检测任务类型（调试→激活 debug skill，编码→激活 tdd skill），在执行中自我约束。它可以叠加在 OpenSpec/SpecKit 之上提供执行纪律，但不解决"做什么"的问题。

**三者的关系不是替代，而是互补**。最实用的组合是：**OpenSpec 管"变什么"，Superpowers 管"怎么执行对"**。OpenSpec 作者明确把 SpecKit 定位为 Greenfield 工具，而自己专注 Brownfield——这揭示了一个深层问题：约定应该锚定在现状（OpenSpec）还是理想态（SpecKit）？

### 为什么人脑可以"脑补"，AI 不能？

这不是精度问题，是**认知机制**问题。

| 能力 | 人脑 | AI（LLM） |
|------|------|----------|
| 理解隐含前提 | 能从"做个登录"脑补出"需要密码加密、会话管理、密码找回" | 只能从训练数据中的统计模式推断，可能推断出错误的默认（如用明文存储密码） |
| 处理模糊性 | 看到"快速响应"会自动根据场景调整预期（内部工具 < 100ms，后台报表 < 5s 都算快） | "快速"没有数值绑定，可能生成不合理的超时配置 |
| 修正偏差 | 读到第 5 页发现和第 2 页矛盾，会回溯修正整体理解 | 没有真正的回溯机制，矛盾信息会被平等对待，导致输出不一致 |
| 社会语境 | 知道"这是给老板看的"vs"这是给新人看的"，调整表达深度 | 没有社会语境感知，除非显式注入 |

**这意味着**：给 AI 的上下文必须**显式、精确、无歧义**，因为 AI 没有"常识补全"能力。它不会在你没说的地方停下来问"这里是不是漏了什么"——它会直接生成，而且生成得很自信。

### 契约形态：人与 AI 的约定应该长什么样？

对比三种工具后，可以提炼出四个判断标准：

**1. 约定必须是可执行的，而不仅是可读的**

SpecKit 的 spec.md 是人读的，AI"参考"它——参考意味着可偏离。OpenSpec 的 delta 标记更接近可执行，因为 AI 可以对照 `MODIFIED` 检查自己是否改对了地方。理想态是：约定应像编译器检查类型一样，AI 能**自检**是否偏离。

**2. 约定应该分层锚定，而不是 monolith**

SpecKit 把 constitution + spec + plan + tasks 放在一个流程里，产出 800 行文档。问题在于**不同层级的变更是不同频率的**：
- Constitution（月级变更）→ 全局约束
- Spec（周级变更）→ 业务契约
- Plan/Task（日级变更）→ 执行细节

每层应有独立生命周期。OpenSpec 的 `specs/` vs `changes/` 分离已触摸到这个思想，但还可以更彻底。

**3. 约定需要双向反馈机制**

当前三者都是"人写/审 → AI 执行"的单向流。但编码过程中 AI 会发现规格中的矛盾（"这个字段在 spec 里必填，但数据库 schema 里没有"），此时应该：
- AI 能**提出规格修正提案**（回到 changes/）
- 人**审批后**规格和代码同步更新

这才是**活约定**——不是写完之后冻结，而是在人机协作中共同演化。

**4. 验证层必须是约定的组成部分，不是附加物**

Superpowers 的 TDD skill 最接近这个理念：测试不是"写完代码后补的"，而是"约束编码行为的先决条件"。但还可以更进一步：

```yaml
spec/
  behavior.md      # GIVEN/WHEN/THEN
  schema.ts        # 类型即契约
  test.contract.ts # 属性测试
  invariant.md     # 不变量（如"订单总额 = ∑ 子项金额"）
```

AI 在实现时，这些验证器同时作为**目标函数**和**约束条件**。

### 从 SDD 到迭代卡片：提取不是复制

**错误的提取**：
```
SDD 第 3 节：系统架构（5 页）→ 复制粘贴到迭代卡片
SDD 第 7 节：数据库设计（3 页）→ 复制粘贴到迭代卡片
```

结果：卡片 300 行，AI 注意力被稀释，关键信息淹没在冗余中。

**正确的提取**：
```
SDD 第 3 节：系统架构（5 页）
→ 提取："严格三层架构，Controller 只做参数校验"
→ 丢弃：架构图、各层职责的详细说明（这些是给人看的）

SDD 第 7 节：数据库设计（3 页）
→ 提取："新增 coupon_template 和 user_coupon 表，字段如下..."
→ 丢弃：ER 图、索引策略的论证过程（这些是给人评审的）

SDD 第 12 节：接口设计（2 页）
→ 提取：精确到字段类型和校验规则的接口契约
→ 丢弃：接口的调用时序图（AI 不需要看图）
```

**提取原则**：
- **保留**：决策（为什么选 A 不选 B）、约束（不能碰的边界）、精确数据（字段类型、错误码）
- **丢弃**：论证过程（这些是给人理解用的）、图表（AI 无法解析）、概述性描述（AI 可以自己生成）

### 回流不是复制

代码产出后，哪些信息应该回流到 SDD？

| 应该回流 | 不应该回流 |
|---------|-----------|
| 实际接口和 SDD 设计有出入的地方（为什么改了） | 具体的实现代码 |
| 验证后发现的技术决策调整 | 单元测试的具体用例 |
| 新发现的业务规则边界 | 调试过程中的中间状态 |
| 性能测试后的数据支撑 | 临时的 workaround |

**案例**：
```
迭代前 SDD：优惠券有效期精确到小时
迭代中实际实现：发现 JavaScript Date 的时区处理有坑，改为精确到秒
回流到 SDD：更新接口文档，注明"精确到秒，ISO 8601 格式，服务端时区"
```

### 双轨制的运行摩擦

双轨制不是自然发生的，需要组织层面的约定：

| 摩擦点 | 表现 | 解决方式 |
|--------|------|---------|
| SDD 更新滞后 | 代码已经改了，SDD 还是旧的 | 把"更新 SDD"作为迭代的最后一个 checklist 项 |
| 提取标准不一致 | 有人复制粘贴，有人精简过度 | 定义提取模板，团队评审前几个实例 |
| 回流信息噪声 | SDD 被大量临时决策污染 | 区分"架构级变更"（回流）和"实现级调整"（不回流） |
| 两套文档的维护成本 | 团队觉得"写两遍"是负担 | 明确分工：PM/架构师维护 SDD，开发者维护迭代卡片 |

**建议的分工**：
- **SDD 作者**（PM/架构师）：关注业务价值、用户流程、系统边界
- **迭代卡片作者**（开发者）：关注代码改动、技术决策、接口契约
- **回流审核**（技术负责人）：决定哪些决策需要从代码侧回流到 SDD

## 五、人的不可替代性：策展人角色

AI 能写代码、能分析、能测试，但有三件事做不了。不是能力不够，而是**这些任务的定义本身就需要人**。

### 1. 价值判断：为什么 AI 不能替代？

AI 可以分析数据（"这个功能的日活用户是 500"），但**不能判断价值**（"500 日活值不值得投入 2 周开发"）。

**根本原因**：价值判断需要**权衡不可量化的因素**——用户满意度、品牌声誉、团队士气、战略优先级。这些因素没有统一度量衡，也无法从代码中推导出来。

**案例**：
```
AI：优惠券系统的技术方案已就绪，预计开发 3 天，测试 2 天。

人：等一下。这个活动是为了清库存，还是拉新？
     如果是清库存，优惠券门槛应该低一些；
     如果是拉新，门槛应该高一些，但优惠力度更大。
     这会影响整个业务规则的设定。

AI：（沉默，因为它没有被注入"清库存 vs 拉新"这个业务背景）
```

AI 不会主动问"这个功能存在的业务理由是什么"，除非人在 Clarify 阶段显式注入。

### 2. 责任承担：为什么 AI 不能替代？

AI 可以生成代码，但**不能对代码的后果负责**。责任不是一个技术问题，而是一个**社会契约**问题。

| 场景 | AI 能做的 | 人必须做的 |
|------|----------|-----------|
| 代码有 bug | 定位问题、生成修复 | 决定是否需要回滚、如何向用户道歉、谁来加班修复 |
| 架构选择有风险 | 列出风险点 | 决定"接受风险"还是"推迟上线" |
| 性能不达标 | 提供优化方案 | 决定"降低性能目标"还是"推迟发布" |

**关键区别**：AI 提供的是**选项分析**，人做的是**承担后果的选择**。

### 3. 模糊意图澄清：为什么这是创造性工作？

"我想要一个流畅的体验"——这句话对 AI 来说等于什么都没说。但对人来说，这句话背后有一整套未言明的期望：

- 流畅是相对于什么而言的？（竞品？旧版本？）
- 流畅的衡量标准是什么？（加载时间？动画帧率？操作步骤数？）
- 流畅的优先级高于什么？（功能完整度？开发成本？）

**AI 的问题**：它会把"流畅"翻译成它能理解的技术指标（如"优化数据库查询"），但这个翻译可能是错的。

**人的创造性工作**：把"流畅"这个模糊意图，通过一系列追问和假设验证，翻译成**可执行的技术约束**。这个过程不是简单的"翻译"，而是**重新定义问题**。

**案例**：
```
用户：我想让优惠券领取更流畅

AI：（可能理解为）优化数据库查询，减少领取接口的响应时间

人：（通过追问发现）用户真正的痛点是"领取优惠券后不知道怎么用"，
     所以"流畅"指的是"领取后自动弹出使用指引"，
     而不是"接口响应更快"
```

### 人的核心身份：策展人（Curator）

在上下文工程中，人的角色不是"编程者"，而是**策展人**——一个决定什么信息值得保留、什么决策值得锚定、什么方向值得探索的策展人。

| 策展工作 | 具体表现 |
|---------|---------|
| **选择保留什么** | 决定哪些决策写入 CLAUDE.md，哪些只留在迭代卡片 |
| **选择锚定什么** | 在注意力稀释前，主动锚定关键决策 |
| **选择探索什么** | 决定 AI 的提案中哪些值得深入，哪些应该否决 |
| **选择沉淀什么** | 决定哪些经验从个人迭代沉淀为团队规则 |

**策展人的反面是"被动响应者"**：AI 给什么就要什么，从不主动注入业务上下文，从不挑战 AI 的假设。这种模式下，AI 不是在协作，而是在**替代**——替代的不是编程工作，而是**思考工作**。

## 六、实践指南

### 6.1 卡片编写原则

**原则 1：精确优于完整**

宁可 5 条精确规则，不要 50 条模糊描述。

| 模糊（无效） | 精确（有效） |
|-------------|-------------|
| "优惠券要有效" | "优惠券必须在有效期内（精确到秒，以服务端时间为准）" |
| "注意性能" | "查询响应时间 < 100ms（P95），否则加 Redis 缓存" |
| "处理错误" | "数据库冲突抛 ConflictError，上游重试最多 3 次" |

**原则 2：决策必须带理由**

AI 会在后续对话中面临类似的决策场景。如果它知道理由，就能在新的场景中做出一致的选择。

```markdown
❌ 差：用乐观锁
✅ 好：用乐观锁（version 字段），冲突时重试最多 3 次
      理由：当前订单量单机事务足够，行锁在高并发下会成为瓶颈
```

**原则 3：显式列出边界**

"不改什么"和"改什么"同样重要。AI 不知道你的隐性边界，它会"顺手"优化它认为"更好"的代码。

```markdown
## 本次改动范围
- ✅ 订单创建流程增加优惠券校验
- ✅ 新增 coupon_template、user_coupon 表
- ❌ 不改支付回调逻辑
- ❌ 不改库存扣减逻辑
- ❌ 不改前端代码
```

**原则 4：假设显式化**

用 checklist 标记尚未验证的假设。这不是给 AI 看的，是**给人自己看的**——防止在迭代过程中忘记验证关键假设。

```markdown
## 待验证假设
- [ ] 优惠券查询是否需要分页？（预计用户持有优惠券数 < 20）
- [ ] 高并发领券场景下，乐观锁重试策略是否足够？
- [ ] 优惠券和会员折扣的互斥规则，是否需要产品确认？
```

**原则 5：约定结构——分层与可执行**

迭代卡片不是唯一形式的约定。根据工具和场景的不同，人与 AI 的约定可以分层设计：

```
┌─────────────────────────────────────┐
│  Constitution（全局纪律）            │ ← 跨项目复用，如 TDD、复杂度上限
│  - 写入 .claude/rules/ 或 SKILL.md   │
├─────────────────────────────────────┤
│  Specs（业务契约层）                 │ ← 活文档 + Delta，OpenSpec 风格
│  - 当前系统行为的结构化描述            │
│  - 变更提案作为显式 diff              │
├─────────────────────────────────────┤
│  Plans（执行蓝图）                   │ ← 动态生成，人审批准后锁定
│  - 从 spec 反推的任务分解             │
│  - 写入迭代卡片的 plan 段             │
├─────────────────────────────────────┤
│  Verification（验证层）              │ ← AI 可自检
│  - 测试、类型、静态分析、不变量        │
│  - 作为约定的组成部分，不是附加物      │
└─────────────────────────────────────┘
```

**关键设计决策**：
- **规格是代码的 peer**——在版本控制中，有 review 流程，不是附属文档。
- **AI 是约定的消费者也是生产者**——执行时发现矛盾，能提案修改规格。
- **验证层是机器可执行的**——人类定义"什么算对"，机器裁决"是否真的对"。

**工具选型速查**：
- 成熟系统加功能 → OpenSpec（Delta 契约）
- 从零构建复杂系统 → SpecKit（完整工作流）
- 已有规格但执行走样 → Superpowers（行为纪律）
- 组合方案 → OpenSpec + Superpowers（规格 + 纪律）

### 6.2 反模式：为什么会发生？

| 反模式 | 深层原因 | 表现 | 对策 |
|--------|---------|------|------|
| **过度细化** | 人不信任 AI 的能力，试图用卡片替代实时对话 | 卡片 300 行，规定到每行代码 | 聚焦"边界和决策"，实现细节留给 Phase 3 的实时博弈 |
| **点头机器** | 人的认知负荷过载，进入"自动驾驶"模式 | AI 问"这样可以吗？"，人不思考就确认 | 设定"强制检查点"：每 10 轮对话必须主动 review 关键决策 |
| **上下文膨胀** | 每次迭代都往卡片里加内容，从不删除 | 卡片越来越长，AI 注意力稀释 | 迭代结束后归档，只把验证过的决策沉淀到 `.claude/rules/` |
| **策展缺位** | 人没有意识到自己的"策展人"角色 | AI 主导对话方向，人被动响应 | 每次启动前明确"本次我的目标是什么"，偏离时主动拉回 |
| **范围蔓延** | AI 的"顺手"建议触发了人的"反正也花不了多少时间"心理 | 迭代中答应了 AI 的额外改动建议 | 回到迭代卡片核对"不改动"列表，任何超出范围的改动必须重新评估 |
| **约定僵化** | 规则写入后不再更新，技术发展后约束过时 | AI 被迫遵循过时的规范，产生不合理代码 | 每月评审 `.claude/rules/`，删除过时的、合并重复的 |
| **工具错配** | 在成熟系统上用 Greenfield 工具，或反之 | 规格与代码脱节，变更追踪困难 | Brownfield 选 OpenSpec，Greenfield 选 SpecKit，执行纪律选 Superpowers |

### 6.4 团队沉淀 Workflow

```
个人会话中发现问题/模式
        ↓
记录到 .claude/iterations/（需求级，短期，1-2 周）
        ↓
若发现可复用模式（经过 2-3 次验证，且至少 2 人认可）
        ↓
提炼到 .claude/rules/（团队级，长期，数月）
        ↓
若影响项目全局决策（技术栈变更、架构调整）
        ↓
更新 CLAUDE.md（项目级，永久）
```

**沉淀的触发条件**：

| 层级 | 触发条件 | 示例 |
|------|---------|------|
| 迭代卡片 → 团队规则 | 同一问题在 2-3 个迭代中被反复纠正 | 连续 3 次 AI 都用了错误码 400 而不是 422，提炼为规则"业务规则不满足用 422" |
| 团队规则 → 项目规范 | 规则影响多个模块或新成员 onboarding | 错误码规范被 5 个模块采用，提升到 CLAUDE.md |
| 项目规范 → 无需变动 | 已成团队共识，无需额外维护 | "用 Prisma" 已成默认，不再需要在每次迭代中声明 |

**避免的陷阱**：
- **过早沉淀**：一次迭代中的"经验"未经充分验证就写入规则，导致错误固化
- **沉淀滞后**：团队成员各自摸索，同样的问题被反复解决，知识没有共享
- **规则僵化**：规则写入后不再更新，技术发展后规则过时

**建议的节奏**：
- 每周五下午 30 分钟：回顾本周迭代，识别可沉淀的模式
- 每月一次：评审 `.claude/rules/` 和 `CLAUDE.md`，删除过时的、合并重复的

## 七、延伸思考

1. **上下文工程能否自动化？** SDD 足够结构化时，能否自动提取生成迭代上下文卡片？
2. **团队知识如何真正沉淀？** 如何让规则更新成为流程的有机部分而非额外负担？
3. **上下文压缩的质量边界**：200K token 窗口足够大，但压缩算法的质量如何衡量和优化？
4. **多智能体协作的上下文传递**：多个 AI 代理并行时，上下文如何同步和合并？
5. **约定的双向演化**：AI 在执行中发现规格矛盾时，如何安全地提出修正提案？人审批的 UI/UX 应该长什么样？
6. **验证层的统一语法**：GIVEN/WHEN/THEN + 类型系统 + 属性测试，能否收敛为一种 AI 原生可消费的契约语言？
